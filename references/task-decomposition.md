# Декомпозиция задачи и отсечение лишней работы

Используй этот документ, когда определяешь, на какие направления (workstreams) делить задачу, и когда проверяешь готовый план на лишнюю работу. Принцип: `minimum sufficient decomposition` — разделяй только то, что действительно независимо, и убирай всё, что не нужно для цели пользователя.

## 1. Размер задачи

Определи размер до декомпозиции. Размер задаёт, какие секции промпта нужны и уместны ли вопросы и сабагенты.

| Размер | Признаки | Следствия |
| --- | --- | --- |
| Малая | Один локальный дефект или правка; один модуль/компонент; дизайн задан существующей системой; результат проверяется одним тестом или одним сценарием в браузере | Один workstream. Без design-аудита, без сабагентов, без вопросов о стратегии выполнения. Секции «Декомпозиция» и «Сабагенты» в промпт не включаются. |
| Средняя | Одна фича в нескольких слоях одной системы (например, компонент + существующий API) или заметный редизайн одного экрана | Обычно 1–2 workstream, последовательные. Сабагенты только если направления действительно независимы. |
| Крупная | Несколько независимых направлений (backend + БД + frontend; design + implementation; миграция + совместимость), несколько подсистем, длинная работа | Явная декомпозиция, вопросы о стратегии выполнения, возможные сабагенты. |

Количество технологий в задаче не определяет размер. «React + CSS + Jest» в одной правке — малая задача.

## 2. Когда делить

Раздели задачу на отдельные workstreams только если для каждого выделяемого направления верно всё перечисленное:

1. У него есть собственный проверяемый результат (тест, контракт, экран, миграция).
2. Его можно выполнить без ожидания результата другого направления, либо зависимость сводится к заранее фиксируемому контракту (схема API, форма данных, дизайн-спецификация).
3. Оно затрагивает свой набор файлов; пересечение с другими направлениями минимально.
4. Его отсутствие в плане ломает Definition of Done.

Если хотя бы одно условие не выполняется — это шаг внутри существующего workstream, а не отдельное направление.

Типовые направления, которые могут быть независимыми: product/design, frontend, backend, database, infrastructure, tests, browser QA, performance, security, migration, documentation. Список не предписывает создавать эти направления; он лишь называет то, что бывает независимым.

### Примеры

- «Редизайн страницы + новый backend API» → `UI/design`, `frontend implementation`, `backend/API`, `integration/QA`. Между frontend и backend фиксируется контракт API до параллельной работы.
- «Система уведомлений: backend API, БД и frontend» → `database` (схема, миграция), `backend` (API, доставка), `frontend` (UI, состояния), `integration/tests` (сквозной сценарий). Схема данных и контракт API фиксируются первыми, потому что от них зависят остальные направления. Если миграция и модель живут в том же слое и каталоге, что и API, `database` допустимо объединить с `backend`; контракт данных при этом всё равно фиксируется первым.
- «Исправить открытие dropdown в существующем React-компоненте» → один workstream: воспроизвести, найти причину, исправить, проверить. Ни design, ни отдельного QA-направления, ни сабагентов.
- «Перевести проект на новую major-версию библиотеки» → `migration` и, если есть публичный API, `compatibility/tests`; отдельный frontend/backend split не нужен, если библиотека затрагивает один слой.

## 3. Design и implementation

Разделяй дизайн и реализацию на отдельные workstreams только когда дизайн является самостоятельной задачей: новая страница или продукт, редизайн, изменение визуального языка, отсутствующая дизайн-система, работа по референсу или скриншоту.

Если разделение уместно:

- **Design**: визуальная концепция, композиция и иерархия, UX-сценарии, responsive-состояния, interaction и motion, соответствие или расширение design system, работа с референсами. Результат — спецификация, по которой можно реализовать интерфейс без новых дизайн-решений.
- **Implementation**: компоненты, state, API и data flow, интеграция, состояния загрузки/ошибок/пустоты, тесты, browser QA. Реализация следует утверждённой спецификации и не переизобретает дизайн.

Не создавай design workstream и не запускай дизайн-аудит, когда изменение локальное и внешний вид задан существующей design system: исправление бага в компоненте, добавление поля в форму по существующему паттерну, новая кнопка в существующей панели. В таких задачах требование к промпту — «следовать существующей design system», а не «спроектировать».

## 4. Work pruning (обязательная фаза)

После первичного плана пройди по каждому workstream и каждому пункту и ответь:

1. Нужен ли он для пользовательской цели?
2. Блокирует ли его отсутствие Definition of Done?
3. Входит ли он в scope, заданный пользователем?
4. Не является ли он необязательным cleanup?
5. Не является ли он рефакторингом ради рефакторинга?
6. Не дублирует ли он другой workstream или шаг?
7. Не существует ли уже готовая реализация в проекте (по данным repository grounding)?

Если пункт не проходит проверку — убери его. Если он полезен, но не нужен, перечисли его в промпте в «Не делать» или как «обнаруженное, но не выполняемое», чтобы целевой агент не добавил его сам.

### Запрещено добавлять автоматически

Не включай в план без прямого запроса пользователя или доказанной необходимости для DoD:

- глобальный рефакторинг;
- переписывание архитектуры;
- новые abstraction layers (интерфейсы с одной реализацией, фабрики, лишние сервисы);
- cleanup соседнего кода;
- новые зависимости;
- новые infrastructure components (очереди, кэши, сервисы, контейнеры);
- документацию, которую пользователь не просил и которая не нужна для эксплуатации результата;
- тесты на несвязанный код;
- redesign соседних экранов;
- «улучшения» производительности или безопасности вне scope (перечисли их как наблюдения, если они значимы).

## 5. Порядок между workstreams

- Сначала фиксируй контракты, от которых зависят несколько направлений (схема данных, API, дизайн-спецификация). До фиксации контракта зависимые направления не запускаются параллельно.
- Последовательный этап, полностью зависящий от предыдущего, не является отдельным workstream для параллелизации и не передаётся сабагенту.
- Integration/QA всегда завершающий этап и остаётся за главным агентом, даже если реализация была распределена (см. [subagent-policy.md](subagent-policy.md)).

## 6. Как отразить в промпте

Включай секцию «Декомпозиция» только для средних и крупных задач. Для каждого workstream укажи: название, результат, границы файлов/подсистем (если подтверждены), зависимости от других направлений и способ проверки. Для малой задачи вместо секции достаточно короткого «Порядка работы».
