# Политика использования сабагентов

Сабагенты не используются автоматически только потому, что среда их поддерживает. Решение принимается по задаче, разрешению пользователя и возможностям целевой платформы (см. `platforms/`).

## 1. Когда сабагенты уместны

Делегируй часть работы сабагентам только если выполняются все условия:

1. Есть минимум два независимых workstream по правилам [task-decomposition.md](task-decomposition.md).
2. Работа достаточно крупная: каждое направление — это несколько файлов и самостоятельная проверка, а не одна правка.
3. Параллельность реально сокращает время или разгружает контекст главного агента (например, широкое исследование репозитория).
4. Результат каждого направления можно проверить независимо.
5. Границы ответственности сформулированы так, что два сабагента не редактируют одни и те же файлы.
6. Пользователь разрешил сабагентов явно или выбранная им стратегия выполнения это предполагает.

Типичные роли: design analysis, backend implementation, frontend implementation, исследование репозитория, test/QA review. Роль должна совпадать с workstream, а не выдумываться отдельно.

## 2. Когда сабагентов не создавать

- Ради одного файла или одной функции.
- Ради простого поиска, который решается grep/чтением за пару вызовов.
- Ради микроправки, где описание задачи длиннее самой правки.
- Для последовательного этапа, полностью зависящего от результата предыдущего.
- Для integration и финальной validation — это работа главного агента.
- Когда пользователь не разрешил делегирование, а среда не даёт его по умолчанию.
- Когда задача малого размера по [task-decomposition.md](task-decomposition.md).

## 3. Роль главного агента (orchestrator)

При включённых сабагентах главный агент:

1. Выполняет repository grounding сам и передаёт сабагентам подтверждённые факты: пути, контракты, соглашения.
2. Определяет scope, декомпозицию и контракты между направлениями до делегирования.
3. Формулирует для каждого сабагента: цель, границы файлов, что запрещено менять, ожидаемый результат и способ проверки.
4. Запускает независимые направления параллельно и продолжает собственную независимую работу (например, интеграционный слой или контракт), а не ждёт вхолостую.
5. Получает результаты, проверяет их по коду и тестам, не принимает вывод сабагента на веру.
6. Интегрирует результаты, устраняет конфликты и расхождения с контрактами.
7. Запускает общую validation: тесты, typecheck/lint/build, runtime/browser-проверку.
8. Несёт ответственность за конечный результат и финальный отчёт.

Вывод сабагента без проверки не считается выполненной работой. Если сабагент сообщил «готово», главный агент проверяет изменённые файлы и результаты проверок сам.

## 4. Как отразить в промпте

Секция «Сабагенты» включается только когда сабагенты разрешены и уместны. В ней:

- перечисли направления, которые делегируются, и направление, которое главный агент делает сам;
- зафиксируй запрет на редактирование одних и тех же файлов разными сабагентами;
- зафиксируй, что integration и validation выполняет главный агент;
- укажи платформенный механизм делегирования из соответствующего файла `platforms/` только если целевая платформа известна; иначе опиши делегирование нейтрально («используй механизм параллельных агентов твоей среды»).

Если сабагенты не уместны или не разрешены, добавь одну строку в «Порядок работы»: «Не создавай сабагентов; выполняй задачу последовательно, параллеля только независимые чтения и проверки».

## 5. Разрешение пользователя

Для крупной задачи, где декомпозиция даёт независимые направления, спроси пользователя (вместе с остальными вопросами о стратегии выполнения, см. `SKILL.md`):

- разрешены ли сабагенты;
- нужно ли явное разделение ответственности между ними в промпте.

Для малой задачи вопрос не задаётся, а сабагенты не включаются. Если пользователь уже ответил ранее или прямо задал стратегию, повторно не спрашивай.
