# Полный шаблон агентного промпта

Используй этот документ при создании каждого промпта. Оставляй только применимые секции, но не теряй обязательные инварианты.

## 1. Рекомендуемая структура

```markdown
# Роль

Назначь агенту конкретную техническую роль, необходимую для задачи.

# Цель

Сформулируй один проверяемый итог, которого должен достичь агент.

# Контекст

- Перечисли только подтверждённый стек, продуктовый контекст и исходные материалы.
- Зафиксируй известные ограничения среды и целевую платформу агента, если она известна.
- Назови существующие референсы, предоставленные пользователем.

# Режим выполнения

Один из режимов из §2 с его формулировкой. Укажи, где агент останавливается и что считается разрешённым без подтверждения.

# Подключённые скиллы

До планирования и действий:

- Для задачи по существующему репозиторию: используй установленный `graphify` до планирования и изменений кода. Запускай его через механизм целевой платформы (см. `platforms/`), либо CLI `graphify`.
- Для greenfield-задачи: не добавляй Graphify, если исследование существующего репозитория не требуется.
- Перечисли каждый выбранный domain skill точным именем и его ответственность в этой задаче; потребуй прочитать инструкции skill полностью до действий.
- Если capability нужна, а skill в среде нет: укажи точную команду установки для целевой платформы, если установка разрешена и безопасна, и потребуй прочитать `SKILL.md` после установки; иначе зафиксируй fallback базовыми средствами.

Используй только подтверждённые доступные и применимые скиллы. Не имитируй работу отсутствующего skill и не утверждай, что он установлен, пока это не подтверждено.

# Repository grounding

(Только для задач по существующей кодовой базе.)

До составления плана и изменения файлов исследуй репозиторий:

- Если доступен Graphify (skill `graphify` или существующий `graphify-out/`), считай его первым источником сведений об архитектуре: entry points, модули, зависимости, вызывающие и вызываемые компоненты, существующие аналоги, тесты, соглашения, blast radius.
- Подтверди выводы чтением затронутых исходных файлов перед редактированием. Graphify не заменяет чтение файла.
- Не придумывай пути и сущности проекта.
- Если Graphify недоступен, завершился ошибкой, не покрывает нужную часть проекта или индекс устарел, выполни fallback: поиск по репозиторию и символам, инспекция зависимостей и конфигурации, чтение исходников. Кратко укажи, почему понадобился fallback.

# Декомпозиция

(Только для средних и крупных задач; см. task-decomposition.md.)

Для каждого workstream: название, результат, границы (подтверждённые файлы/подсистемы или процедура их обнаружения), зависимости от других направлений, способ проверки. Контракты между направлениями (схема данных, API, дизайн-спецификация) фиксируются первыми.

# Scope

## Сделать

- Перечисли конкретные результаты, прямо требуемые пользователем.

## Не делать

- Назови соседние системы и функции, которые нельзя менять.
- Исключи необязательный рефакторинг, cleanup, новые зависимости, новые слои абстракции, новую инфраструктуру, документацию и тесты вне scope, redesign соседних экранов.
- Перечисли то, что было отсечено на этапе work pruning, если агент может попытаться добавить это сам.

Запрос пользователя определяет границы работы. Не расширяй и не сокращай scope молча. Обнаруженные посторонние дефекты не исправляй, если они не блокируют задачу; перечисли их отдельно в финальном отчёте.

# Функциональные требования

1. Опиши наблюдаемое пользовательское или системное поведение.
2. Зафиксируй обязательные состояния и обработку ошибок.
3. Укажи требования совместимости и сохраняемое существующее поведение.

# Технические ограничения

- Сохраняй существующую архитектуру, naming, форматирование и паттерны, если задача прямо не требует их изменить.
- Предпочитай минимальные точечные патчи переписыванию целых файлов.
- Не добавляй зависимости без доказанной необходимости.
- Не меняй публичные контракты и unrelated-код без требования задачи.

# Сабагенты

(Только когда сабагенты разрешены и уместны; см. subagent-policy.md.)

- Делегируемые направления и направление, которое главный агент выполняет сам.
- Разные сабагенты не редактируют одни и те же файлы; каждому передаются подтверждённые пути и контракты.
- Главный агент проверяет результаты по коду и тестам, интегрирует их и выполняет общую validation.
- Механизм делегирования — из адаптера платформы, если платформа известна.

Если сабагенты не уместны, вместо секции добавь строку в «Порядок работы»: «Не создавай сабагентов; параллель только независимые чтения и проверки».

# Порядок работы

1. Исследуй фактическое состояние проекта через Graphify, исходники и подключённые скиллы.
2. Составь короткий исполнимый план на основе найденных данных, затем убери из него всё, что не нужно для цели и Definition of Done.
3. Действуй по режиму выполнения: остановись после плана или выполни всю работу в рамках запроса. В autonomous-режиме не проси разрешения на очевидные, обратимые и необходимые действия.
4. Независимые чтения, поиски, проверки и команды выполняй параллельно, когда между ними нет зависимости.
5. Если часть задачи заблокирована, выполни все остальные независимые части до сообщения о блокировке.
6. Перед завершением проверь: если финальный текст описывает то, что ты ещё собираешься сделать, сделай это сейчас (кроме режима «только план»).

# Проверка

- Запусти наиболее релевантные существующие тесты.
- Выполни применимые typecheck, lint и build.
- Проверь изменённое поведение в рантайме или браузере, если это возможно и относится к задаче.
- Для найденной регрессии добавь или обнови сфокусированный тест, если тестовая инфраструктура уже существует и это входит в scope.
- Не утверждай, что результат работает, без проверки. Если проверка невозможна, точно укажи, что и почему не удалось проверить.

# Definition of Done

Задача завершена только когда:

- Все запрошенные состояния и сценарии реализованы (или, в режиме «только план», план покрывает их все).
- Существующее затронутое поведение не сломано.
- Релевантные проверки проходят.
- Нет незапланированных изменений за пределами scope.
- Финальный diff просмотрен на лишний код и случайные изменения.

# Финальный ответ

Кратко сообщи:

- что изменено;
- что и какими проверками подтверждено;
- какие допущения были сделаны;
- какие блокировки остались;
- какие посторонние проблемы обнаружены, но намеренно не исправлялись.
```

### Какие секции включать

| Размер задачи | Обязательно | Исключается |
| --- | --- | --- |
| Малая | Роль, Цель, Контекст, Режим выполнения (одна строка), Скиллы (только если реально нужны), Repository grounding (для существующего repo), Scope, Требования, Ограничения, Порядок, Проверка, DoD, Финальный ответ | Декомпозиция, Сабагенты |
| Средняя | То же + Декомпозиция, если направлений больше одного | Сабагенты, если направления зависимы |
| Крупная | Все применимые секции | Ничего по умолчанию; всё равно убирай неприменимое |

## 2. Режимы выполнения

Режим выбирается на шаге 5–6 `SKILL.md` и фиксируется в секции «Режим выполнения». Формулировки ниже — основа; платформенные способы включения режима см. в `platforms/`.

### Plan only

Агент исследует и проектирует, выдаёт план и ничего не реализует. Формулировка: «Не изменяй файлы и не выполняй команд, меняющих состояние проекта. Результат — план с направлениями, порядком, рисками и критериями проверки. После плана остановись». DoD в этом режиме — полнота и проверяемость плана. Секция «Проверка» описывает, как план будет проверяться при реализации, а не запуск тестов.

### Plan → approval → implementation

Агент исследует, строит план, останавливается и ждёт подтверждения; после утверждения (в том числе с правками пользователя) реализует. Формулировка: «Выдай план и остановись. Реализацию начинай только после явного подтверждения пользователя; учитывай его правки. После подтверждения работай автономно до Definition of Done». Если целевая платформа имеет plan mode, укажи его.

### Autonomous implementation

Агент исследует, формирует внутренний рабочий план, реализует, интегрирует и проверяет без подтверждения обратимых шагов. Формулировка: «Выполни всю задачу в текущем ходе. Не останавливайся после плана и не спрашивай подтверждения на обратимые действия внутри scope. Спроси только при необратимых действиях, выборе внешнего провайдера, вопросах безопасности или существенно разных вариантах продукта». Режим по умолчанию для правок и фич, если пользователь не просил план.

Режим по умолчанию: пользователь просил «план/архитектуру/оценку» — Plan only; просил «сделай/исправь/реализуй» — Autonomous implementation; неясно и задача крупная — спросить (шаг 5 `SKILL.md`).

## 3. Обязательные поведенческие инварианты

Встраивай их по смыслу, не обязательно дословно.

### Завершение работы

- Агент завершает всю запрошенную задачу в выбранном режиме, насколько это позволяют доступ и инструменты.
- Он не заканчивает словами «следующим шагом», «могу продолжить» или просьбой подтвердить очевидное действие (кроме остановок, предусмотренных режимом).
- Разрешение пользователя выполнить задачу уже покрывает обратимые действия, непосредственно необходимые для неё; оно не даёт права расширять scope.

### Разумная автономность

- Рутинные неоднозначности разрешаются по существующему коду и соглашениям проекта.
- Вопрос задаётся только при существенно разных результатах, необратимых действиях, выборе внешнего провайдера, требованиях безопасности или недостающих полномочиях.
- Наличие одной блокировки не останавливает независимую работу.

### Экономные изменения

- Точечный patch предпочтительнее полной перезаписи при одинаковом результате.
- Существующий баг, cleanup, deprecated API или возможность оптимизации не исправляются автоматически, если не мешают текущей задаче.
- Архитектура меняется только при прямой необходимости, подтверждённой исследованием.
- План проходит work pruning: всё, что не нужно для цели и DoD, удаляется.

### Параллельность

- Перед обращением к инструментам агент определяет независимые запросы.
- Независимые чтения файлов, Graphify-запросы, поиски, инспекции и проверки объединяются или запускаются параллельно.
- Зависимые действия сохраняют корректный порядок.
- Сабагенты — только по политике `subagent-policy.md`; главный агент проверяет и интегрирует их результаты.

### Проверка актуальности

- Быстро меняющиеся библиотеки, модели, API, инструменты и платформы агентов проверяются по текущей официальной документации.
- Поиск по интернету не заменяет исследование локального репозитория; Graphify не заменяет чтение конкретного файла перед правкой.

## 4. Адаптация по типу запроса

### Реализация

Сделай требования наблюдаемыми: что пользователь сможет сделать, какие состояния увидит, какие ошибки будут обработаны. Укажи затрагиваемые системы только если они подтверждены пользователем; иначе поручай найти их через repository grounding.

### Диагностика или review

Не давай агенту полномочия автоматически исправлять найденное, если пользователь просит только анализ. Требуй доказательства: путь, символ, связь вызовов, воспроизведение, лог или тест. Выводы разделяй по критичности и уверенности.

### Архитектура

Потребуй сначала восстановить фактическую архитектуру и ограничения. Сравни варианты по сложности, стоимости миграции, риску, эксплуатации и обратимости. Не внедряй выбранный вариант без отдельного запроса на реализацию (режим Plan only, если не сказано иное).

### Frontend и дизайн

Опиши не абстрактное «сделай красиво», а иерархию, композицию, состояния, адаптивность, доступность и визуальную проверку. Для существующего интерфейса сохраняй дизайн-систему, если редизайн не запрошен; design workstream и дизайн-аудит — только по правилам `task-decomposition.md` §3.

Добавляй следующие ограничения, когда они относятся к стеку:

- не использовать `transition-all`;
- не анимировать `box-shadow` крупных элементов без необходимости;
- использовать тени через design tokens, без случайных arbitrary shadow;
- для moving-layer отделять shadow-layer;
- проверять `overflow-hidden` у родителей анимируемых элементов;
- не добавлять `will-change` без измеримой причины;
- проверить hover, modal, card, dropdown и tooltip в браузере;
- поддержать `prefers-reduced-motion` для существенной анимации.

### Design + implementation

Когда дизайн — самостоятельная задача: сначала design workstream с результатом-спецификацией (композиция, состояния, responsive, interaction, токены), затем implementation по спецификации, затем browser QA. Реализация не переизобретает дизайн; дизайн не описывает код.

### Full-stack фича

Зафиксируй первыми контракты: схема данных и миграция, контракт API, затем backend, frontend, интеграционный сценарий и тесты. Каждое направление имеет собственную проверку; сквозной сценарий проверяет главный агент.

### Скриншоты и визуальные референсы

Потребуй анализ полного кадра, затем crop/zoom навигации, типографики, ключевых компонентов и спорных участков. Агент не должен делать точные выводы о мелких деталях по уменьшенному изображению.

### Agent harness и длинные задачи

Только для задач по созданию агентной системы добавляй:

- история сообщений append-only;
- старые сообщения и thinking/tool blocks не переписываются;
- при compaction сохраняются решения, отвергнутые варианты, ограничения, имена, пути, числа, даты, ссылки, точные формулировки, текущее состояние и незавершённая работа;
- после compaction агент продолжает с текущего состояния, а не начинает заново.

## 5. Контроль качества готового промпта

Перед выдачей проверь:

- цель одна и проверяема;
- режим выполнения указан и не противоречит «Порядку работы» и DoD;
- repository grounding закреплён до плана и изменений для существующего репозитория, с fallback;
- скиллы выбраны по capabilities, названы точно, подтверждены средой или помечены как устанавливаемые/fallback;
- отсутствуют выдуманные файлы, зависимости, skills, платформенные команды и факты;
- декомпозиция минимальна: нет направлений без собственного результата, нет design workstream для локальной правки;
- work pruning выполнен: нет рефакторинга, cleanup, зависимостей, инфраструктуры, документации и тестов вне scope;
- сабагенты включены только по политике и с разрешения; orchestrator проверяет результаты;
- scope содержит как «Сделать», так и значимые «Не делать»;
- требования описывают результат, а не декоративную активность агента;
- проверка соответствует стеку и реальному риску;
- Definition of Done можно проверить;
- секции, не относящиеся к задаче, исключены;
- нет просьбы выполнить очевидные следующие шаги позже (кроме остановок по режиму);
- нет плейсхолдеров и многоточий.
